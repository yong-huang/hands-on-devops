# 12 · 终极串联：demo-web 的双通道观测闭环

> 把入库、可视化、告警三条线的零件装回一台机器：demo-web 服务每个请求走 HEC 直报（JSON）+ 文件日志（UF 采集）双通道汇入同一索引，配仪表盘与两条告警；故障演练 kill 服务 → 下线告警送达 → 重启 → 对账恢复。读完你能带走：一套完整的"服务观测闭环"参考实现，和三个可复跑的闭环断言。

## Background

单个实验回答单个问题：数据怎么入库、字段怎么解析、告警怎么送达。真实运维问的是另一个问题——**一个服务倒下时，观测系统能多快告诉我**。这需要把入库（两种通道）、可视化、告警三条线在同一份真实数据流上接起来，并做一次"真 kill"演练。

之前的实验刻意拆散了组件；本实验反向操作：以 demo-web（模拟被观测服务）为圆心，HEC 直报结构化事件、UF 采集文件日志、双通道汇入同一索引，仪表盘消费、告警值守，最后用故障演练验证闭环的每一环都在岗。

## What

观测闭环的组件清单与实测结论（演练全程自动化）：

| 组件 | 载体 | 作用 |
|:---|:---|:---|
| demo-web | Python stdlib 服务（宿主 :28330） | 被观测目标：/hit 正常、/boom 报错 |
| 通道 1：HEC | 每请求直推 JSON → loop_demo | 结构化事件（seq/status/latency） |
| 通道 2：UF | 文件日志 → monitor → 9997 TLS → loop_demo | 同请求的行式镜像 |
| 仪表盘 | Studio JSON（lab 10 模式） | 双通道时序 + 通道占比（对账用） |
| 告警 ×2 | 应用包（lab 11 模式） | 错误率 >20%、服务下线（3 分钟无数据） |

可以把双通道想象成"同一笔账记两本账簿"——HEC 账簿记结构化明细、UF 账簿记原始行。但和记账不同，两条通道的写入者是同一个服务的同一个请求，理论上必然 1:1；对账断言（A）就是拿这个不变量做证据：**UF 行数 = HEC 数 = 文件行数，差额 0**。

演练实测：kill 服务 → `service_down` 告警 54 秒送达（≤300s）；重启 → 双通道对账恢复差额 0。

## When to Use

- **给一个服务接观测**：本实验的组件清单就是"从零到闭环"的最小完备集，按端口/索引改名即用
- **验证观测系统本身**：kill 演练证明"服务没了会被告警看见"——观测系统的可用性也要被观测
- **何时不用**：单组件排障用前 11 个实验的针对性断言更快；生产演练要做变更窗口与降级预案，不能只 kill

| 验证方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 闭环演练（本实验） | 端到端 + 故障注入，断言可复跑 | 服务观测上线验收 |
| 单组件针对性断言（labs 01-11） | 快、聚焦单环节 | 排障定位某一段链路 |
| 手工点选巡检 | 零脚本、不可复跑 | 临时抽查 |

三条闭环断言与实验的对应关系：

| 断言 | 证明什么 | 对应实验 |
|:---|:---|:---|
| 对账差额 0 | 双通道计数一致、无丢事件 | lab 04/07 |
| 告警送达 <300s | 下线被观测系统看见 | lab 11 |
| 重启后对账恢复 | 闭环是持续过程而非一次性 | 本实验 |

## Quick Start

前置：lab 01 实例 + UF 镜像（lab 08 同款拉取命令）。

```bash
cd splunk/12_spl_full_loop
./spl_full_loop.sh all   # up → ufup → webup → traffic → reconcile → drill → clean
```

`reconcile` 与 `drill` 的真实输出（节选）：

```
=====> [reconcile] 双通道对账（UF 行数 = HEC 数 = 文件行数，差额 0）
        文件行数 50 | UF 通道 50 | HEC 通道 50
        ✅ 断言 A：双通道对账一致（UF=50，HEC=50，各等于文件行数 50，差额 0）
=====> [drill] 故障演练：kill demo-web → 下线告警送达 → 重启恢复
        [ok] demo-web 已 kill（00:59:07），基线送达 4 次
        下线告警送达 2026-11-19 01:00:01（search_name=service_down）
        ✅ 断言 B：kill → service_down 告警送达（54s ≤ 300s）
        ✅ 断言 C：重启后对账恢复（差额 0）
```

诚实预期：`all` 约 18-25 分钟——大头是 UF 首次引导（约 10 分钟）与下线告警送达等待（cron */1 每分钟裁决，实测 kill 后 54 秒送达）；演练含一次 kill 与两轮 50 请求流量。

kill 前的"基线送达 N 次"是索引重建后到首流量落地前 service_down 的空窗误报（索引为空 → 最近 3 分钟无数据 → 每轮 cron 必中），次数随 UF 引导时长浮动，脚本只把它当 kill 的时间分界、不参与断言。

`clean` 删 UF 容器、loop_demo 索引、HEC/告警配置并重启，全组件归零。

## How It Works

**双通道的不变量**。demo-web 对每个请求同时做两件事：HEC 直报一条 JSON（`time` 取请求时刻）+ 文件追加一行（同一时刻的文本镜像）。

两条通道的解析路径完全不同（lab 07 的 JSON 协议 vs lab 08 的文件 monitor），但事件数必须同为请求数——断言 A 拿这个不变量当证据：任何一条通道丢事件，对账立即超差。

**服务下线告警的时间窗**。demo-web 的事件时间是当前时钟（与教程数据的固定时间不同），因此下线告警用 `dispatch.earliest_time = -3m` + "count=0" 条件：最近 3 分钟该索引无任何事件即触发。

kill 后的送达时刻由"最近 3 分钟无数据"条件首次成立之后的下一轮 cron 决定，上限约 4 分钟（3 分钟窗口排空 + 60 秒调度）——断言 B 的 300s 上限即按此设定，实测 54 秒。

**演练的自动化结构**。drill 步骤按时间顺序推进：记 kill 时刻与送达基线（基线=演练前已送达的告警文件数，区分演练前后送达）→ kill → 轮询接收器直到出现 `search_name=service_down` 的载荷 → 断言送达时延 →
 重启 demo-web → 补流量 → 重跑对账。

全程无人工介入，演练记录即脚本输出。

## Pitfalls & Q&A

- **双通道对账别用"合计=请求数"**：重启演练后流量翻倍，合计会变 200 而断言 50 必炸。解法：对账基准用**文件行数**（UF 通道天然等于它），HEC 通道各自对齐
- **观察期判"下线"要用当前时钟**：教程数据事件时间固定在过去，时间窗搜索永远为空——本实验 demo-web 的事件时间即当前时钟，`-3m` 窗口才成立（与 lab 11 的恒真条件对照：数据时间与真实时钟脱节时用恒真，一致时用时间窗）
- **演练流量混入前次计数**：kill 前后的送达基线要先记录（断言 B 用送达时刻差而非计数）；演示事件与业务事件用 path/search_name 区分（lab 07 同款）

**Q1：为什么两条通道汇入同一索引而不是分索引？** 对账要"同一份数据的两个视角"在同一处相加：`stats count by sourcetype` 一条查询同时给出两侧计数。分索引则要两次查询再手工合并，断言复杂度翻倍。

**Q2：demo-web 为什么用 stdlib 而不用 FastAPI？** 被观测服务的实现语言与观测链路无关——HTTP 端口 + 日志文件才是观测系统看到的全部。stdlib 版零依赖、任何机器秒起，把注意力留给闭环本身；真实服务换成 FastAPI 不影响任何断言。

**Q3：这一环如果 UF 停机（而非 demo-web 停机），对账会怎样？** UF 停机期间文件继续增长，复启后续传补齐（lab 08 的机理）——对账最终仍为 0 差额，只是到达延迟。这正是双通道 + 对账断言的价值：区分"服务真丢了事件"与"链路延迟送达"。
