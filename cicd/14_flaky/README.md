# 14 · flaky test 治理——重试、识别与隔离

> flaky test = 同一代码、不同结果：`random() < 0.5` 的随机失败让它时绿时红。
> 重试（pytest-rerunfailures）能**掩盖**它——失败后重跑最多 3 次，多数轮次
> 照样发绿；但掩盖不等于治愈：总有重试耗尽仍红的一轮，把整条流水线拖死。
> 治理 = 从重试证据里识别 flaky → 进隔离名单 → 流水线恢复全绿，同时保证
> 真失败（断言恒错）不会被重试或隔离洗白。
>
> 本实验 10 轮 × reruns=3 实测：3 轮被掩盖、1 轮耗尽仍红、隔离后 10/10 全绿。

## Background

flaky test 是 CI 信任的头号杀手：第一次红你会查，第三次红你会点 retry，
第十次红团队学会了对红色免疫——真失败也就此淹没在噪音里。

治理的第一步不是修 flaky（根因可能是并发、时序、共享状态），而是先把
它从主流水线里**识别出来并隔离**，让绿色重新有意义；同时必须证明隔离
机制对真失败无效——否则名单就成了掩盖工具。

## What

**定义**：flaky = 重试可翻绿的失败；真失败 = 重试后仍红。治理管道 =
`重试运行 → RERUN 证据 → 名单 → 隔离` 四步。

| 环节 | 实现 | 实测 |
|:---|:---|:---|
| 重试 | `--reruns 3`（rerunfailures） | 3/10 轮被掩盖，1/10 轮耗尽仍红 |
| 识别 | 解析 `-rR` 摘要的 RERUN 行 | 检出 `test_flaky_order`（4/10 轮重试） |
| 隔离 | `--deselect=<nodeid>` | 隔离后 10/10 轮全绿，稳定用例零误伤 |
| 不误放行 | 退出码断言 | 恒错用例 RERUN ×3 + exit 1 |

重试像止痛药：吃了不疼（绿了）但病灶还在，药效一过（重试耗尽）照疼。
隔离像把传染病人转出病房——不是治好他，是让其他人安全，等根因修复后
再移回名单。

失效边界：类比没覆盖"名单会过期"——隔离只是止血，flaky 用例躺在名单里
永远不修，就等于永久删除了这条测试。名单必须定期审视（见 Q&A）。

## When to Use

- 团队已经出现"红了就 retry"的文化：先把 flaky 从噪音变成显式名单；
- 大型测试集（千级用例）：单个 flaky 每天浪费的排查时间远超治理成本；
- 反例：测试总量少、失败全部值得人查——隔离是奢侈品，直接修根因即可；
  flaky 根因清晰且一行能修的，修掉比进名单更快。

## Quick Start

前置：python3 + pytest + pytest-rerunfailures（`pip install
pytest-rerunfailures`）。

```bash
cd cicd/14_flaky
./flaky_pipeline.sh              # 全程：detect → report → quarantine → broken → clean
#                                （无参全流程最后会清日志；想分步观察请单跑各段）
./flaky_pipeline.sh detect       # 10 轮 × reruns=3，观察随机失败的真面目
./flaky_pipeline.sh report       # 解析重试证据 → flaky 报告 + 隔离名单
./flaky_pipeline.sh quarantine   # 名单生效：10 轮全绿断言
./flaky_pipeline.sh broken       # 真失败不误放行：退出码断言
./flaky_pipeline.sh clean        # 清日志
```

`detect` 段的真机取证（10 轮完整输出见脚本运行日志）：

```
        第 6 轮：绿，但发生了重试（flaky 被掩盖）
        第 9 轮：红（重试耗尽仍失败）
        [ok] 检测完成：3 轮重试掩盖、1 轮重试耗尽仍红
```

`report` 段生成的报告与名单：

```
flaky 检测报告（10 轮 × reruns=3）
  发生重试的轮数: 4/10
  重试耗尽仍红的轮数: 1（flaky 的本质：重试掩盖不了全部）
  检出 flaky 用例（按重试发生轮数排序）:
    - tests/test_flaky.py::test_flaky_order  (4/10 轮重试)
```

诚实预期：随机失败每一轮的分布都不同（本例 3 掩盖 1 耗尽，下次可能是
2 掩盖 3 耗尽）；不变式是"重试证据存在 → 名单收 flaky → 隔离后全绿 →
真失败仍 exit 1"。

## How It Works

### 重试引擎：掩盖率的算术

`--reruns 3` 下，失败率 0.5 的用例单轮逃过惩罚的概率是 `1 - 0.5⁴ ≈
93.75%`——十轮里期望约 0.6 轮漏网。实测 1/10 轮重试耗尽仍红，与算术
吻合。重试次数越多掩盖越彻底，但 0.5ⁿ 永远大于 0：重试没有治愈能力。

### 证据与名单：RERUN 行是唯一线索

`-rR` 让 pytest 在短摘要里列出每次发生重试的用例（`RERUN <nodeid>`）。
`flaky_report.py` 扫 10 轮日志、按 nodeid 聚合重试次数、生成隔离名单
`quarantine.txt`——名单精确到 nodeid 而不是文件，避免误伤同文件里的
稳定用例。

### 隔离与不误放行：两条相反的保证

隔离轮用 `--deselect=<nodeid>` 摘掉 flaky，10 轮全绿证明名单生效且
稳定用例零误伤；恒错用例单独跑：重试 3 次后 `exit 1`、RERUN 恰好 3
次——重试机制对真失败无能为力是**正确行为**，退出码 1 保证流水线 FAIL。

## Pitfalls & Q&A

- **① 只加重试不加证据 = 系统性说谎**：`--reruns` 单独使用时，3/10 的
  轮次里失败被静默消化、流水线发绿——退出码 0 会让你以为一切正常。重试
  必须搭配 `-rR`（或插件报告）留证据，否则 flaky 连被识别的机会都没有。
- **② 名单精确到 nodeid，不能到文件级**：`--ignore tests/test_flaky.py`
  会连文件里的稳定用例一起扔掉；`--deselect=<nodeid>` 才是外科手术。
- **③ 隔离不能只增不减**：名单只进不出 = 用例永久死亡。每次隔离要挂
  issue（本实验名单在 report 输出中带轮数统计），根因修复后移出并回归
  验证——名单是急诊室，不是坟场。

Q&A：

- **重试次数怎么定？** 由可忍受的漏网率反推：失败率 p、重试 n 次，漏网
  率 pⁿ⁺¹。p=0.5、n=3 → 6.25%/轮；要压到 1% 以下需要 n≥6——但每次重试
  都在拉长流水线，预算和掩盖率是显式交易。
- **flaky 的根因通常是哪些？** 并发共享状态、时序依赖（sleep）、外部
  服务、随机数据未固定种子。本实验的 `random()` 是最纯的模拟——治理
  管道与根因无关，先隔离再从容修根因。
- **为什么不用 pytest-randomly / xdist 顺手治？** 它们是"让 flaky 更容易
  暴露"的手段（乱序、并发压出竞态），与"把已暴露的 flaky 摘出主流水线"
  是两个阶段——暴露在前、隔离在后，工具不互相替代。
