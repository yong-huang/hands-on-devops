# 10 · 金丝雀发布——三档晋级与错误率门禁

> 金丝雀（canary）= 只把一小撮真实流量放给新版本试探：先 10%，观察没问题
> 加到 50%，再全量 100%。全程有一个自动门禁盯着**真实错误率**——一旦超过
> 阈值（本实验 10%），立刻把流量全部撤回稳定版。发现问题的瞬间就止损。
>
> 本实验复用 09 的双槽拓扑，把"一次性切槽"换成"带权重的渐进放量"：
> 三档晋级每档打 1000 请求断言分布，再注入 5xx 看门禁自动止血。

## Background

09 的蓝绿是"要么全蓝要么全绿"——对 v2 的信心只来自预部署体检，真实用户
第一次踩到它就是 100% 流量的那一刻。体检绿不等于服务健康（见 Pitfalls ②）。

金丝雀的思路是让真实流量替你试错：小比例放量，用生产指标（错误率、延迟）
当验收标准。人肉盯屏来不及反应，所以要有**自动门禁**：指标越界即中止晋级，
流量机械地退回稳定版——止损速度以秒计，不等人类起床。

## What

**定义**：金丝雀发布 = 加权分流 + 分档放量 + 指标门禁。流量分配的单位是
`upstream`（声明后端服务器列表的配置块）里的 `weight`，晋级是单调放大
金丝雀权重，中止是摘除金丝雀。

| 档位 | upstream 配置 | 实测分布（1000 请求） |
|:---|:---|:---|
| 第一档 90/10 | `blue weight=9; green weight=1` | v1 × 900 / v2 × 100 |
| 第二档 50/50 | `weight=1; weight=1` | v1 × 500 / v2 × 500 |
| 第三档 100% | 仅 `green`（blue 摘除，不 stop） | v1 × 0 / v2 × 1000 |

可以把金丝雀想成"新厨师先做一桌试菜"：不是让全店客人吃新菜单（蓝绿），
也不是砸了旧菜单重学（原地升级），而是每十桌先给一桌上新菜——难吃就立刻
停掉，只有一桌人的差评，不是全店差评。

失效边界：这个类比没覆盖"发牌精度"。实测三档偏差都是 0.0pp，因为本实验
edge 只有 1 个 worker、nginx 平滑加权轮询按周期精确发牌（9:1 即每 10 个
请求恰好 1 个进 v2）；多 worker / 长连接复用的生产环境有采样噪声，所以
断言放宽到偏差 < 10 个百分点，而不是奢求 0。

## When to Use

- 新版本行为未知（重构、依赖升级、新算法）：需要真实流量验证再放量；
- 有能自动采集的质量指标（错误率、P95 延迟）：门禁才有判断依据；
- 故障要求"发现即止损"：中止是摘权重，秒级完成，比回滚部署快得多。
- 反例：新旧版本无法低量混跑（schema 不兼容、缓存结构变了）——10% 的
  用户打到不兼容版本就是 10% 的真实故障；样本太少的低流量服务，10% 档
  一小时只有几十个请求，错误率噪声比信号大，门禁形同虚设。

## Quick Start

前置：Docker（本机 daemon 已启动）、curl、python3。nginx 镜像首次运行
自动拉取。

```bash
cd cicd/10_canary_gate
./canary.sh              # 完整生命周期：up → promote → abort → clean
./canary.sh up           # 起双槽 + edge，断言基线 100% v1
./canary.sh promote      # 三档晋级，每档 1000 请求断言分布偏差 < 10pp
./canary.sh abort        # 注入 v2 5xx → 门禁超阈值 → 自动中止回 v1
./canary.sh clean        # 销毁环境，配置复位
```

`promote` 段的真机取证（完整输出见脚本运行日志）：

```
        [ok] 第一档 90/10：1000 请求 → v1 × 900 / v2 × 100（green 10.0% vs 配置 10%，偏差 0.0pp < 10pp）
        [ok] 第二档 50/50：1000 请求 → v1 × 500 / v2 × 500（green 50.0% vs 配置 50%，偏差 0.0pp < 10pp）
        [ok] 第三档 100% green：1000 请求 → v1 × 0 / v2 × 1000（green 100.0% vs 配置 100%，偏差 0.0pp < 10pp）
```

`abort` 段的真机取证：

```
        [ok] 门禁采样 300 请求：非 200 × 150（错误率 50.0% > 阈值 10%）→ 自动中止晋级
        [ok] 止血后 1000 请求全量 v1（v2 × 0）——中止即秒回稳定版
        [ok] green 直连仍 503——回滚是切走流量，不是修好故障（修槽是另一件事）
```

诚实预期：0.0pp 得益于单 worker 的确定性发牌，复跑可能看到零点几个百分点
的抖动；门禁错误率 50.0% 是 50/50 权重下注入全量 5xx 的必然值。断言的
不变式是"偏差 < 10pp"与"超阈值必中止"，不是这些具体数字。

## How It Works

### 权重切分：upstream weight 与平滑加权轮询

```nginx
upstream app {
    server blue:80 weight=9;
    server green:80 weight=1;
}
```

nginx 默认用平滑加权轮询（smooth weighted round-robin）：不是"连发 9 个
blue 再发 1 个 green"，而是在每个发牌周期里把请求均匀打散。单 worker 下
9:1 配置跑 1000 请求就是精确的 900/100——分布断言敢设 < 10pp，因为本
实验里它是确定性计算。

### 指标门禁：度量的是 edge 上的真实错误率

门禁采样 300 个打到 edge `/api` 的请求，统计非 200 占比，超过阈值 10%
就触发中止。它看的是**用户实际收到什么**，而不是槽自己说自己健康不健康
——这是金丝雀门禁与部署前体检的本质区别。

### 故障注入：覆写 green 的站点配置

green 槽的 `default.conf` 挂载的是 `green_active.conf`：注入 = 用
`slot_v2_bad.conf` 覆写它再 reload green。坏配置里 `/api` 返回 503、
`/version` 仍返回 200——模拟"健康检查全绿、业务路径全挂"的故障形态。

### 自动中止：摘权重，而不是修故障

`abort` 段先回到 50/50（模拟放量中途出事），注入后门禁测得错误率 50.0%，
随即把 `active.conf` 覆写为仅含 blue 并 reload edge——1000 个验证请求
全量 v1。`proxy_next_upstream off` 在这里至关重要（见 Pitfalls ①）。

## Pitfalls & Q&A

- **① 重试配置会吞掉故障信号**：`proxy_next_upstream` 默认仅
  `error timeout`（连接层错误才换下一台），503 会如实透传；但若有人加
  `http_503`/`http_5xx` 这类"提高可用性"的重试，503 会被静默换成 blue
  的 200——错误率恒 0、门禁失明。分流处显式 `off` 兜底。
- **② 健康检查绿 ≠ 服务健康**：注入的坏配置 `/version` 仍返回 200，
  green 的 healthcheck 全程 healthy；只有门禁度量的业务路径 `/api` 在
  报错。健康检查覆盖"进程活着"，覆盖不了"功能正确"。
- **③ 覆写 bind mount 的单文件用 `cat >`**：`mv` 替换会换 inode，容器里
  看到的还是旧内容；`cat >` 原地覆写保 inode，green reload 前文件已可见。

Q&A：

- **金丝雀和蓝绿（项目 9）怎么选？** 蓝绿是"全有或全无"的切换，回滚快但
  验证靠体检；金丝雀用真实流量分档验证，风险敞口小，但要能混跑、要有
  可信指标。生产里常见组合是"金丝雀验证 + 蓝绿/滚动放量"。
- **阈值 10% 怎么定？** 看基线噪声：稳态错误率 0.1% 的服务，阈值设 1-5%
  都合理；本身就有 2% 错误率的服务，阈值得高于基线 + 抖动，否则天天误杀。
  原则：阈值 = 基线 × 数倍，而不是拍脑袋的固定数。
- **为什么实测分布能精确到 0.0pp？** 单 worker + 平滑加权轮询的确定性：
  9:1 权重的发牌周期是 10 个请求，1000 请求 = 100 个整周期。多 worker 或
  连接 keep-alive 粘住单 worker 时会有小噪声——阈值放宽到 10pp 就是给
  这些现实因素留的余量。
